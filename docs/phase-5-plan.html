Phase 5, Planned

Phase 4 ended with a function that returns five relevant chunks. Phase 5 turns that into something that answers — and this is the plan's dense LangGraph paragraph, unpacked.

Planned · not started 18 Aug 2026 ~2 evenings Local · per-query API cost

What Phase 5 actually is

Three things a person would recognise:

  • A dispatcher that reads your question and decides where the answer lives — the SQL tables, the semantic index, or both.
  • Three fetchers, one per destination, that go and get the material.
  • A writer that reads what came back and produces an analyst-quality answer with citations that resolve to real source text.

Wired together as a small graph, so each piece is separately testable and the whole thing has one entry point.

Query answering — on demand, read path

Questionplain text, unlabelled
Intent routersmall model · sees the text, never the corpus
route: sql counts, filters, dates — “how many Aave proposals passed last quarter?” silver · Iceberg
route: vector open-ended themes — “what are the arguments against fee switches?” pgvector
route: hybrid precise constraint plus qualitative judgment silver → pgvector
Analyst synthesisstrong model · structural citations
Answer + resolvable sources

The router reads the question and nothing else. It never touches the corpus — a router that had to query data in order to decide how to query data would be circular and expensive. It sees a sentence, emits one label, and steps aside. That is why it can run on a small cheap model while only synthesis needs a strong one.

Why a router at all

Different questions have different shapes, and the shapes need different tools.

“How many Aave proposals passed in the last quarter?”

Arithmetic over structured fields. proposal_versions already has proposal_state, voting_end and protocol_name — a SELECT count(*) … WHERE answers it exactly. Semantic search would be a terrible way to count things: it returns five chunks that talk about proposals passing, and counting those gives you five.

“What are the arguments against protocol fee switches?”

There is no column for “arguments against”. This is what the embeddings are for.

“Which Aave proposals last quarter changed risk parameters, and what did the forum argue about them?”

Both — a date and protocol filter, then the qualitative debate. This is the phase's demo question.

The pieces, one at a time

The state object

Every node reads and writes one shared dictionary.

class AgentState(TypedDict):
    messages: Annotated[Sequence[BaseMessage], add_messages]
    question: str
    route:    Literal["sql", "vector", "hybrid"]
    filters:  dict                 # protocol, dates, source — from the router
    rows:     list[dict]           # what the SQL node found
    chunks:   list[SearchResult]   # what the vector node found
    answer:   str
    citations: list[str]

The add_messages annotation is not decoration. The original blueprint had a docstring where this belongs. Without a reducer LangGraph overwrites messages on each node's return instead of appending — so conversation history silently vanishes and every turn looks like the first.

The router node

Input: the question. Output: a label plus any filters it can confidently extract.

{"route": "hybrid", "protocol": "aave", "since": "2026-05-01", "source": null}

Small model, temperature 0, JSON-constrained. The filters are a real bonus: Phase 4 measured protocol="aave" taking a failing question from 0/3 to 2/3.

The SQL node

Translates the question into a query against silver via Trino. Two hard rules:

  • WHERE is_current unless the question is historical. Silver is SCD2, so without it a proposal edited three times is counted three times.
  • Never let the model emit raw SQL against a live connection. Constrain it to parameterised templates — count, list, filter-by-date, top-N. A template covers the real question shapes and cannot be talked into DROP TABLE.

The vector node

Calls search() exactly as Phase 4 left it — the layer that already works and is already measured. That is the whole point of having built it standalone first.

The hybrid node

Runs both, and the ordering matters: SQL first, then vector within its results. Get the 14 Aave proposals from last quarter, then search semantically inside that set — rather than searching everything and hoping the date filter is honoured.

The synthesis node

Two things carry over verbatim from the original blueprint because they are genuinely good.

The three-dimension structure. Governance questions have technical, economic and political dimensions, and covering all three is what makes an answer analyst-grade rather than a summary: “this changes the LTV parameter” (technical), “reducing borrowing capacity by ~$40M” (economic), “proposed by the risk service provider over delegate objections” (political).

The DATA GAP IDENTIFIED escape hatch. Phase 4 measured exactly why this matters: one question retrieves a chunk about revenue projections for a question about founder compensation, at a distance no threshold can reject. Synthesis is the last line of defence, and the one component that can actually read the text and notice.

Citations that structurally cannot be faked

“Cite your sources” is an instruction, not enforcement. Instead make citations part of the output contract, then validate after generation: every marker in the prose must exist in the citation list, and every chunk_id must resolve to a chunk actually retrieved for this question.

{
  "answer": "Aave deprecated oracles for long-tail assets [c1], which
             delegates argued would strand positions [c2].",
  "citations": [
    {"marker":"c1", "chunk_id":"…", "document_id":"0xaa68…", "source":"proposal"},
    {"marker":"c2", "chunk_id":"…", "document_id":"25400",  "source":"forum"}
  ]
}

A hallucinated citation fails a lookup rather than reaching the user. That check is a unit test, not a hope.

What Phase 4 measured that changes this design

Four findings that should shape Phase 5 rather than be rediscovered inside it.

1. Set k by question shape — free, and the largest available win

Thematic misses are a ranking problem, not an absence problem:

Thematic recallk=5k=10k=20k=50
documents found ÷ expected0.780.830.941.00

Every expected document is already retrieved; it just sits below the cut. Someone asking “which protocols pay delegates?” expects a list, not five items. The router is the first component that knows a question is thematic, so it is the right place to set k=20 while a lookup question keeps k=5. Verified: negatives stay clean at 5/5 for k=5, 10 and 20, because the accept/reject decision is computed on the raw top-10 profile regardless of k.

2. Use the model as a relevance judge, not a reranker

Measured, on the exact pair no threshold can separate:

QuestionTop relevance scorePassages ≥2
“How much is the Aave founder paid?” — should return nothing00
theme-delegate-incentives — should return 4 documents37

Total rejection and total confidence — a clean split where the distances (0.451 vs 0.458) have the two in the wrong order.

But the same model reranking for order made thematic recall worse (0.78 → 0.72): it optimises “does this passage answer the question”, so it prefers one deeply detailed protocol over the spread of documents a cross-protocol question needs. Judge, don't reorder. Measured cost ~$0.0004/query.

2b. Route is not enough — the router also decides scope

The three routes answer which store. They do not answer how wide, and for thematic questions that second dimension matters more than the first. Two questions, both vector, needing opposite handling:

QuestionCorrect handling
single-protocol“What is Aave doing to reduce risk surface?”rank globally; do not spread across protocols
cross-protocol“Which protocols run programs to pay delegates?”guarantee every protocol is examined

Getting it backwards is actively harmful — fan-out applied to a single-protocol question loses documents, because slots are reserved for protocols with nothing to say:

Questionflat k=5fan-out 4×5
theme-protocol-fee-expansion (Uniswap)4/43/4
theme-v4-rollout (Uniswap)4/43/4

2c. For “which protocols…”, fan-out beats a bigger k

A question of that form asks for coverage, not ranking. One ranked list structurally cannot guarantee each protocol a fair look — a single protocol's vocabulary can dominate it. Fan-out changes the retrieval shape to match the question's shape: one search per protocol, filter applied, then assemble.

Strategycross-protocol recalldocuments returned
flat k=206/710
fan-out 4 × 56/715
fan-out 8 × 57/730

Flat k=20 and fan-out fix different questions — one needs depth, the other breadth. Only fan-out at depth 8 gets both, at 3× the analyst's context.

The stronger argument for fan-out is not recall — it is that fan-out can answer the question's negative half. “Which protocols?” implies naming the ones that have nothing. A flat ranked list cannot report an absence; a per-protocol search can, because that protocol was searched specifically and returned nothing above threshold.

"What are DAOs doing with idle treasury funds?"
  Uniswap    accept   best 0.464
  Arbitrum   accept   best 0.357
  Aave       —        best 0.548   nothing above the cutoff
  Optimism   —        best 0.524
  ENS        —        best 0.493

That is a directly usable answer. Twenty ranked chunks are not.

2d. Warning — the cutoffs were fitted on unfiltered searches

Applying a protocol filter changes the candidate pool, which changes the distance profile, which changes the threshold verdict. The constants do not transfer:

"Which protocols are running or debating programs to pay delegates?"
  UNFILTERED  best 0.458  gap 0.020
  Aave        best 0.587  gap 0.033
  Uniswap     best 0.506  gap 0.012
  Arbitrum    best 0.458  gap 0.020
  Optimism    best 0.496  gap 0.055
  ENS         best 0.498  gap 0.019

Filtering to one protocol makes results more homogeneous, so the gap narrows for reasons unrelated to answerability. Any Phase 5 node that applies a filter must re-validate the cutoffs for the filtered case, or use the relevance judge instead of the thresholds.

Fan-out therefore inherits the one known false rejection rather than fixing it — the delegate question is rejected under every filter above, exactly as it is unfiltered. The judge resolves that, not the retrieval shape.

Sample-size caveat: only 2 of the 5 thematic eval questions are genuinely cross-protocol. These numbers are suggestive, not settled — growing that group is the cheapest way to decide this on evidence rather than two data points.

3. Protocol filtering belongs to the router

Phase 4 tested whether chunk text alone could fix protocol bleed. It could not. The filter works — 0/3 → 2/3 — but applying it needs the question parsed, and a wrong guess excludes the right answer entirely. That is a decision requiring intent, which is what the router produces.

4. Routing introduces a brand-new error source

Today a question is “thematic” because a human labelled it. In Phase 5 it is thematic because a model guessed. A misrouted question gets the wrong k, the wrong store, possibly the wrong protocol filter — and every Phase 4 number was measured without that error existing. Left unmeasured, misclassification is precisely the kind of invisible failure this project keeps finding.

The routing eval set — build it before the router

Fifteen questions labelled with the branch they should take. Same method as Phase 4: write the measurement first, so “the router works” is a number.

It is genuinely new work, not a relabelling. The Phase 4 eval set contains no SQL-shaped questions at all — no counts, no date ranges, no “how many” — because Phase 4 had no SQL branch to test. The two taxonomies are different axes:

Phase 4 kindsPhase 5 routes
AsksWhat is it about, and is it answerable?Which store can answer it?
Valueslookup · thematic · cross_source · negativesql · vector · hybrid

Target shape: 5 SQL, 5 vector, 5 hybrid, with deliberate near-misses — “how many proposals mention risk parameters” looks like a count but needs semantics, and belongs in hybrid. Those boundary cases are where routing accuracy is actually decided.

Build order

  1. Routing eval set — 15 labelled questions. Measurement first.
  2. State + graph skeleton — nodes returning canned values, .compile(), terminal edges. Prove the graph runs end to end before any node is real.
  3. Router node, measured against the eval set. Iterate the prompt until ≥80%.
  4. Vector node — thin wrapper over search(), with k from the route.
  5. SQL node — parameterised templates over silver, is_current enforced.
  6. Hybrid node — SQL first, vector within its results.
  7. Synthesis node + the citation validator.
  8. gov ask "…" — terminal chat, mirroring gov search.
  9. Re-run make eval to confirm Phase 4 retrieval has not regressed.

Steps 2 and 3 are where the blueprint's shipped code failed outright — it never called .compile(), routed to three undefined nodes, and had no END edge, so the module raised on import and the API never started. Doing the skeleton first makes that class of error impossible to carry forward.

How we will know it works

Exit criteria: the router selects the correct branch on ≥80% of the 15-query routing set, and every factual claim carries a resolvable citation — enforced by the validator, so a hallucinated chunk_id fails a lookup rather than reaching a user.

Cost — and the first thing that can run up a bill

ComponentModelRough cost
Routersmall, cheapnegligible — one sentence in, JSON out
Relevance judgesmall, cheap~$0.0004 (measured)
Synthesisstrongthe dominant per-query cost
Retrieval—one embedding call, fractions of a cent

Embeddings were a one-time corpus cost. LLM calls are per question, so a loop or a retry storm is the first thing in this project that can run up a bill. The existing provider spend cap stays essential.

Open decisions

  • Which model for synthesis. Deliberately deferred — it is a one-client swap, and the router/judge economics do not depend on it.
  • Whether the relevance judge is its own node or folded into synthesis. Separate is cleaner to test and is the component with a measured number attached; folding it in saves a call. Leaning separate.
  • Conversation memory scope. add_messages makes multi-turn possible; whether Phase 5 exposes follow-ups or stays single-shot is a product decision, not a technical one.

What this phase does not do: no FastAPI (Phase 6), no dashboard, no scheduling, no contract source. Phase 5 ends at a terminal command that answers a governance question with citations — the point at which the plan notes “working product from here.”
