A genuine hybrid answer: date and protocol bounds from SQL, qualitative material from the vector store, four resolving citations, and cross-source evidence — three proposals plus a forum thread.

It did not look like that on the first run.

Seven bugs that shipped fluent, confident, wrong output

01Every citation was unresolvable

The prompt showed passages as [0] ref=proposal:0xaa68…#3 and asked the model to echo the ref. It cited "0" — the bracket index. The answer was authoritative, well-structured, and every single citation failed to resolve.

The model no longer supplies a source identity at all. Passages are labelled [c0], [c1]; it selects a marker from that list, so a fabricated citation fails a dictionary lookup. Asking a model to reproduce an opaque string is avoidable when it could just pick a label.

02Hybrid narrowing could never happen

SQL returned 2 titled row(s) but no ids, so no narrowing

list_proposals selected title but not proposal_id, so the hybrid node had no identities to narrow to. The date filter was decorative.

Select proposal_id. Visible only because the node reports what it did.

03The router excluded half the evidence it was asked for

For “…and what did the forum argue about them?” the router set source: "proposal". That excluded every forum post — while the answer went on to describe “forum discussions”.

A question mentioning both sources must leave source null; setting it removes the other half of the evidence outright.

04“The last quarter” resolved to 2023

since: 2023-07-01 ← on a corpus whose newest proposal is Aug 2026

The router had no notion of today, so it invented a plausible-looking date.

Interpolate today's date into the prompt. A live test asserts the resolved year is within one year of now.

05Narrowing deleted all forum evidence

"specific arguments from the forum are not provided in the evidence"

Restricting vector results to the SQL result's ids sounds right — but templates query proposal_versions, so those are proposal ids and no forum topic can ever match one. Narrowing by that set silently deleted every forum chunk, for a question that asked precisely for them.

Narrow only the source the constraint ranged over. Proposals are filtered by the id set; forum chunks pass through.

06Counting questions refused to answer

route: sql · rows: 5 · answer: "DATA GAP IDENTIFIED"

A pure-SQL question routed correctly, ran the right template, got the right rows — and refused. The citation contract was built around text passages and demanded a marker on every claim. With no passages, the model correctly concluded it had nothing citable.

Structured rows are authoritative and need no marker — their provenance is the query. A design gap, not a prompt tweak: one provenance model applied to two branches.

07Answers claimed truncation that never happened

_snippet compared len(" ".join(words)) against summed line lengths. That loses one space per line break, so every multi-line text was marked …. Harmless in a search listing; on an answer it implies the analyst said more than is shown.

Track truncation explicitly, pinned by a test asserting content round-trips unchanged.

Two eval-set errors, found by running it

The routing set was written before the router — which is the point — but writing a benchmark is itself error-prone, and the first run exposed two bad items rather than two bad answers.

My label was wrong. I labelled “Why were Chainlink price feeds deprecated for long-tail assets?” as scope: one, reasoning it is an Aave thread. But the question names no protocol — for the router to know that, it would have to read the corpus, which it must never do. The label demanded knowledge the router structurally cannot have.

Rule now written down and enforced by a test across the whole set: scope: one requires a protocol identifiable from the question text alone.

The item was ambiguous. “What are the currently active proposals about?” was labelled hybrid — but title is a column, so SELECT title WHERE proposal_state='active' genuinely answers it. Two defensible answers means the item cannot discriminate a good router from a bad one. Replaced with one testing the same boundary unambiguously.

Neither was fitting the test to the model: one label contradicted the router's own contract, the other had no single correct answer.

Decisions worth recording

The router emits scope, not just route

The plan's three routes answer which store. Phase 4 showed that is not enough — a thematic question also needs a width, and getting it wrong regresses in both directions: fan-out on a single-protocol question loses documents (4/4 → 3/4), while a flat search on a cross-protocol one misses documents no k recovers.

Retrieval disables the cutoffs; the judge decides

Phase 4 fitted the relevance constants on unfiltered searches. Applying a protocol filter shrinks the candidate pool and narrows the gap for reasons unrelated to answerability. Rather than re-fit per filter combination, nodes retrieve with cutoffs off and the relevance judge decides.

Backed by measurement: on the one pair no threshold separates (0.451 unanswerable versus 0.458 answerable — in the wrong order), judging scored 0 versus 3. The same model reranking for order made thematic recall worse (0.78 → 0.72), so it judges and does not reorder.

The model picks templates, never writes SQL

Six parameterised templates; the model chooses a name and typed parameters. Every value is NULL, a clamped integer, or a validated enum. Injection attempts are rejected, not escaped. Every template is asserted to constrain is_current, with a guard in render() so a future template that forgets it fails loudly.

Known limitations

  • One routing miss remains (0.93). route-active-concerns drops the “currently active” constraint. Deliberately not chased — tuning a prompt against the 15th item of a 15-item set is exactly the overfitting this project keeps catching.
  • is_current cannot currently be demonstrated. Silver holds 0 superseded rows — the corpus was harvested once and nothing changed. The test skips explicitly with that message rather than passing vacuously.
  • The judge costs a call per query (~$0.0004). LLM calls are per question, unlike the one-time embedding cost, so the provider spend cap stays essential.
  • Multi-turn is possible but unused. add_messages accumulates correctly (proven by test); gov ask is single-shot.

What this says about method

Every one of the seven bugs was found by running the thing and reading the output carefully, not by a test failing. The tests came after, to stop them returning. Two patterns recur:

Provenance is where the interesting failures live. Three of the seven — unresolvable citations, deleted forum evidence, refused counting questions — were about where a claim came from rather than whether it was right. Retrieval quality gets measured obsessively; provenance quietly did not, until a validator was pointed at it.

A guard that reports its reasoning beats one that silently succeeds. The narrowing bug was visible only because the node writes a retrieval_note; the citation bug only because the validator names what failed to resolve. Both would otherwise have looked like slightly thin answers.
