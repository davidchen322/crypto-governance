Phase 2 — Ingestion

Snapshot and Discourse clients writing raw API responses into a content-addressed bronze layer. The phase turned on one question: why did a re-harvest keep writing objects for threads nobody had edited?

zero writes on re-harvest · 78 tests

Verdict

The exit criterion was "running the harvest twice produces zero duplicate bronze objects, and a 429 is retried rather than fatal." Five harvests, each with the reason for any non-zero row.

Runs 3 and 5 each wrote nothing and left the object count unmoved. Run 4's full rewrite was the expected consequence of changing the field projection — the content hash is the key, so editing the projection renames every object exactly once.

The 429 half of the criterion is covered by deterministic unit tests against a fake transport rather than by waiting to be throttled in the wild.

78 tests — 42 unit, 22 integration, 14 live contract tests.

Bronze layout

snapshot/space=aavedao.eth/<proposal_id>/<content_hash>.json
discourse/space=gov.uniswap.org/<topic_id>/<content_hash>.json
_manifests/<run_id>.json

No date appears in a data key. That is the entire idempotency mechanism: an unchanged document hashes to a key that already exists, so the write is skipped; an edited document hashes differently and lands beside its predecessor rather than overwriting it.

Bronze therefore accumulates version history as a side effect — which is what Phase 3's SCD2 tables are built from, and what makes an embedding-model change replayable without re-fetching anything. Timestamps live only in run manifests, deliberately outside the data prefixes.

The finding that shaped the phase

The first re-harvest wrote 19 Discourse objects despite nothing having been edited. Diffing two stored versions of the same topic explained it.

Pass one — topic-level noise

suggested_topics904×
views4×
timeline_lookup3×
message_bus_last_id1×

None of that is governance content. suggested_topics is a randomised "related threads" sidebar, views is a hit counter, message_bus_last_id is a realtime cursor. Discourse decorates every response with request-scoped state, so hashing the raw payload made an unedited thread look edited on every fetch.

The fix: hash a content projection, store the full response. Identity comes from the governance content; the body written to object storage is still the complete, unmodified API response.

The duplicate was visible in the data as two objects for topic 1385 with identical byte size and different hashes — later confirmed to be exactly the raw-hash and projected-hash versions of the same content.

Pass two — the same problem one level down

Topic-level noise vanished, but a diff restricted to same-projection versions found it persisting inside post_stream.posts:

posts[].reads32×
posts[].readers_count32×
posts[].score22×
posts[].posts_count20×
posts[].incoming_link_count6×
posts[].trust_level1×

That posts_count is the author's forum-wide tally, which moves when they post in any other thread — not the thread's own reply count.

Run 3 had already passed without this fix, because its window was short. Over a daily schedule read counters move on every active thread, which would manufacture phantom "edits" for Phase 3's SCD2 build to trip over. prune gained a [] wildcard so paths can traverse lists, and those six fields were excluded.

The guard against over-pruning

Deliberately not excluded, because they move only on real activity: topic-level posts_count, last_posted_at, like_count, word_count, participant_count, and post-level reactions, actions_summary, link_counts. Four tests pin both directions — read counters must not create versions; edited bodies and new replies must.

Snapshot vote churn is real, not noise

Two proposals rewrote during run 1. Diffing them showed genuine state change rather than another decoration problem.

0x4ec0c13baf55472ecd53…   state=active
    votes          55         ->  56
    scores_total   210039.0   ->  230224.0

Both state=active. This is correct behaviour and the data is wanted — vote trajectory feeds the voting-centralization analysis the platform exists for.

The consequence for the exit criterion is worth stating precisely: zero-duplicate re-harvest holds strictly for closed proposals. Active ones legitimately version as votes arrive, and the SCD2 design in Phase 3 is built to absorb exactly that.

Deviations from the plan

Bronze keys are not date-partitioned

The plan specified source/space/ingest_date/. A date in the key makes tomorrow's unchanged re-harvest a duplicate by construction, which contradicts the same plan's own exit criterion. Keys are content-addressed instead; the harvest date lives in run manifests.

aave.eth does not exist

The real space is aavedao.eth. An id that silently returns nothing is indistinguishable from a working pipeline with no new proposals, so a live contract test now asserts every configured space exists and has a non-zero proposal count.

Compound swapped for ENS

Compound has 36 Snapshot proposals — it governs mostly on-chain — against ENS's 98 and a far busier forum. Better data for identical effort.

A live test marker was added

Contract tests against Snapshot and Discourse are excluded from make verify; a red build caused by someone else's maintenance window teaches nothing. They run deliberately via make verify-live, and their job is catching upstream API drift — the likeliest way ingestion breaks silently.

Known gaps

Rate limits are assumed, not measured

60/min for Snapshot and 30/min per Discourse host are conservative guesses. No 429 was ever observed, so the retry path has never fired against a real server — only against the fake transport.

Changing the projection rewrites everything once

The content hash defines the key, so editing the excluded-field list invalidates every existing object. This happened twice during Phase 2 and accounts for runs 1 and 4. Acceptable for an append-only layer, but it should be a deliberate decision rather than a casual edit. A scheme version in the key was considered and rejected as premature.

Only the recent window is harvested

Twenty proposals and fifteen topics per protocol, not full history — Aave alone has ~970 proposals. A full backfill is a rate-budget exercise rather than a code change, and is better done once Phase 3 can consume it.

Full topic bodies require an explicit flag

Without --with-posts only listing metadata is stored, which contains no post text. Easy to forget; Phase 3 should fail loudly on a topic object with no post_stream.
