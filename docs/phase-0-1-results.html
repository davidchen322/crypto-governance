Deviations from the plan

Four, in the order they surfaced.

1 · The catalog image publishes no tag below 1.8.1

The plan named apache/iceberg-rest-fixture:1.6.0 to match Iceberg 1.6.1 Spark jars. That tag does not exist — the Apache image starts at 1.8.1. Both sides moved to 1.9.2 so the catalog and Spark runtime stay version-matched.

The plan's underlying advice held: tabulario/iceberg-rest:1.6.0 does exist, but it is the unmaintained Tabular image. The Apache one is the right long-term choice.

2 · The catalog image has no Postgres JDBC driver

The headline Phase 1 requirement — metadata surviving a restart — needs the catalog backed by Postgres rather than its default jdbc:sqlite::memory:. The stock image bundles only the SQLite driver:

java.sql.SQLException: No suitable driver found for
jdbc:postgresql://postgres:5432/iceberg_catalog

Adding the driver is not sufficient on its own. The image's CMD is java -jar iceberg-rest-adapter.jar, and -jar makes the JVM ignore both -cp and $CLASSPATH. The custom Dockerfile adds the driver and replaces CMD with an explicit classpath invocation of the same main class.

3 · A file mount inside a read-only directory mount fails

The first attempt mounted storage/vector_schema.sql into /docker-entrypoint-initdb.d/, a directory already mounted :ro:

error mounting ... create mountpoint for
/docker-entrypoint-initdb.d/01-vector-schema.sql
mount: read-only file system

storage/ is now mounted at /opt/storage:ro and the init script applies the DDL with psql -f, keeping storage/ the single source of truth rather than duplicating schema into the docker directory.

4 · apache/spark leaves its bin directory off PATH

docker compose exec spark spark-sql fails with executable file not found. Fixed with an ENV PATH line in the image rather than hardcoding /opt/spark/bin/spark-sql in the test — the container should behave the way someone typing into it would expect.

The negative control

A harness that always passes is worthless, so the suite was run against a deliberately broken stack: the catalog reverted to the source blueprint's ephemeral SQLite backing, everything else unchanged.

Why this matters

The broken stack reported healthy at every stage and passed every probe that did not involve a restart. Nothing short of tearing the containers down and asserting on what came back would have caught it — which is the entire argument for the harness being shaped this way.

What the checks actually assert

None of them read docker compose ps.

Phase 0 — 18 tests

Git is initialized; .env is not tracked (a .gitignore entry added after staging does not untrack a file); every os.getenv key in application code appears in .env.example; every ${VAR} in the compose file is documented; required files exist; verify.sh is executable.

Phase 1 probes — 9 tests

Postgres, MinIO and the catalog are probed from the host, so a broken port mapping fails. Spark is probed inside its container, since it reaches MinIO and the catalog over the compose network — the two views catch different classes of misconfiguration.

  • pg_isready is treated as liveness only. The real assertion runs pgvector's cosine operator and builds an HNSW index, which is what Phase 4 will depend on.
  • MinIO gets a write / read / delete round trip, not a list_buckets call.
  • The catalog is asserted via GET /v1/config, the actual REST spec endpoint. An open TCP port is not a working catalog.
  • Spark creates a namespace and table, inserts and selects — then MinIO is inspected directly to confirm real .parquet and Iceberg metadata landed. That guards the case where the catalog records a table but S3FileIO wrote somewhere else.

Persistence — 4 tests

Run only after docker compose down, never restart. restart does not remove containers, so it cannot distinguish state held in a named volume from state held in a container's writable layer.

Known gaps

CI is unverified

The workflow is written but has never run — there is no GitHub remote yet. It is unproven until the repo is pushed.

Healthchecks are liveness, not correctness

Deliberately. The iceberg-rest check is a /dev/tcp port probe and the spark check only confirms the Iceberg jars exist in the image. They sequence startup; the integration suite is what proves the services work. This split is documented in the compose file, but it does mean docker compose ps alone should never be read as evidence.

Memory headroom is thin

Docker Desktop reports 8.3 GB on this machine, with spark.driver.memory at 2g. Phase 7 adds Airflow to the same host — that is where the budget gets tight and a bump or compose profiles may become necessary.

First run is slow

A clean machine pulls roughly 2.5 GB and builds two images. The Spark base alone is 1.56 GB and took several minutes here.

Reproducing

make verify     # ~3 minutes once images are cached
